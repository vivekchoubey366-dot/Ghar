Trust & Security

Security at GHAR

Security is built across authentication, authorization, documents, payments, property workflows and platform operations.

1. Account Security

Users should protect passwords, OTPs, sessions and other authentication credentials. GHAR will not intentionally request a user's password through ordinary support communication.

2. Authentication

The planned GHAR architecture supports secure authentication controls including password hashing, OTP expiry, login attempt limits and secure sessions or tokens.

3. Authorization

Access to buyer, seller, tenant, administrative, document and other protected resources should be enforced server-side. Frontend visibility must never be treated as authorization.

4. API Security

  • Rate limiting.
  • Helmet/security headers.
  • CORS restrictions.
  • Request validation.
  • Output sanitisation.
  • Secure cookies where applicable.
  • CSRF protections where applicable.
  • Object-level authorization.

5. File Security

Uploaded property images, videos, documents, agreements and verification files should be subjected to appropriate file-type, size and access controls. Malware scanning should be used where available and appropriate.

6. Administrative Security

Administrative functions should use separate authentication, role-based permissions, audit logging and restricted access. Administrative secrets must never be exposed in frontend code.

7. Fraud and Abuse

GHAR may use automated and manual controls to identify suspicious activity, duplicate listings, unusual account activity, malicious content and potential fraud.

8. Responsible Disclosure

If you discover a security issue affecting GHAR, report it through the official GHAR support/contact channel with enough information for the security team to investigate.

Security principle: Never place passwords, database credentials, API keys, JWT signing secrets or payment provider secrets inside HTML, CSS or client-side JavaScript.
